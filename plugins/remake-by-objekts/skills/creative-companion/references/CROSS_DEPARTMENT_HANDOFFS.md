# Cross-department handoffs: one finding, one decision owner, several consumers

> 0.38 reading rule: these fields are the internal analysis/handoff completeness check. The main client review is a coherent argument about the whole, using ordinary language; do not print repeated source/operation/acceptance labels, IDs or a 22-row ledger by default. Technical schedules belong in an explicitly useful appendix. Current SKILL and PRODUCTION_AUDIT_ENGINE govern presentation.

Use the stable `01`–`22` IDs from `DEPARTMENT_CONTRACTS_22.json`. They identify functions, not required employees or a linear curriculum. A creator may own several functions; a qualified specialist may be needed for one narrow issue. The older 15-stage educational pipeline is not the ID map. Do not duplicate work or fees because the same decision appears under several department names.

REMAKE's primary output is a supported audit and executable professional scope, including where objekts could be useful if capability and capacity are confirmed. Do not silently replace the author's work with a complete screenplay. Full original screenplay generation belongs to a later separately scoped SKRIPT function.

## Handoff packet

Create a packet only for a real affected decision, not for all 22 functions by default. Use the smallest sufficient authorized material. Never treat a public reference as cleared for reproduction or transfer private source material automatically.

| Field | Required content |
| --- | --- |
| Finding | Stable ID, observation or explicitly open risk/dependency, exact source version and scene/asset/time locator. |
| Intent and invariants | Governing author/commission goal, exact underlying source when relevant, what is approved and what may change. |
| Decision owner | One actual accountable person/function; if unknown, mark unknown. Execution ownership is separate. |
| Proposed intervention | Causal professional solution, its meaningful tradeoff, and any viable simpler route. State what existing work already suffices. |
| Work unit | Named affected scenes/assets/versions, count only if known, counting rule if unknown, reusable setup versus per-unit work. |
| Inputs and boundary | `OBSERVED`, `NOT_PROVIDED`, `CONFIRMED_ABSENT`, `CONFLICTING` or `NOT_APPLICABLE` for relevant inputs. Explain completeness/authority limits. |
| Receiver | Responsible function, required specialist skill if justified, and actual availability only if confirmed. |
| Return artifact | Specific inspectable result and source/version correspondence, not “make it more cinematic.” |
| Acceptance | Relevant review context, observable criterion, actual reviewer and test status. Human artistic judgment is not certified by a checklist. |
| Dependencies | What blocks this unit, what can proceed independently and what becomes stale if it changes. |
| Decision history | `PROPOSED`, `APPROVED_BY_OWNER`, `REJECTED` or `SUPERSEDED`, with real provenance. Keep implementation and approval independent. |

The JSON diagnostic examples are conditional mechanisms. Locate evidence and consider intentional form before applying one. A hypothesis becomes `SUPPORTED_DEFECT` only when the material and scope justify that conclusion. Distinguish missing from the submitted set from absent in a complete relevant work; a complete screenplay cannot establish the absence of an external licence. `SATISFIED_FOR_SCOPE` applies only to checked requirements, not the whole department. No blanket `MISSING_BY_DEFAULT`, inferred completion percentages or manufactured gaps to sell services.

## Decisive interfaces and return conditions

### 1. Purpose → concept → scene (`01/02 → 03/04/05`)

**Send:** the governing artistic/commission purpose, verified claim/source evidence, audience hypotheses explicitly labelled and current concept. **Owner:** author/commissioner for purpose; creative lead for proposed execution. **Return:** a concept-to-event map showing how the film expresses the purpose and what cannot yet be verified. Return the packet for a decision if two actual approvers demand incompatible priorities. Do not invent a business objective for a poem or fiction short. A purpose change flags only affected messages, scenes and versions for revalidation; preserve reusable visual work.

**Acceptance:** the actual owner selects the governing priority and can identify its intended screen expression. That agreement does not prove audience response or commercial effect.

### 2. Underlying source → script/edit/sound (`18/20 + source owner → 04/05/17`)

**Send:** exact source/track/version, inspected description/text/audio separately, known use boundaries and authorial invariants. Public availability is not permission. **Return:** a diagnosis grounded in that source and a bounded repair route preserving its governing relationships, unless the owner actually chooses an adaptation departure. If source meaning is unresolved, identify the exact dependency and complete only supported analysis.

**Acceptance:** consequential changes trace to verified context or an explicit owner decision. Hearing a preview, reading a description and reading lyrics are different evidence. Neither source-context compliance nor a revised script is proof of a successful film.

### 3. Script/form → staging → sequence (`04/05 → 06/10/17`)

**Send:** what each consequential scene/recurrence does, whose knowledge matters, chosen form and intentional ambiguity. **Return:** playable action or purposeful non-action, shot entry/exit states, transition logic and a timed test where timing is the uncertainty. Return an irreducible structural problem to the author instead of covering it with more beautiful shots.

**Acceptance:** a practitioner can reconstruct the intended relation without inventing an unprovided event; a timed review assesses the actual experience. Associative, musical, observational and abstract structures need their own relations, not imposed plot causality. Full-work critique must retain a whole-work verdict rather than ending at one micro-fix.

### 4. Identity + world + object → action/camera (`07/08/09 → 06/10/11`)

**Send:** authoritative anchors and allowed changes, functional object states, necessary geometry, current action and source rights boundary. A mood frame is not a floor plan. **Return:** a staging/camera plan that can execute the action while preserving required identity and object truth. Return a conflict when a costume/space/prop makes the action impossible; do not silently change the story or master.

**Acceptance:** representative angles and an actual action/rehearsal/previs test support the relation. A single still cannot prove hand contact, acting, eyeline timing or physical feasibility. Live-action location, costume fitting and scene-specific safety require real appropriate people, not an AI sign-off.

### 5. Performance + geometry → animation (`06/10 → 13/14`)

**Send:** performance objective, pose/action phases, timing, contact anchors, required camera views and deliberate stylization. **Return:** a representative animated interval or real route test, with rig/deformation/control requirements separated from performance quality. An operator who makes attractive frames is not automatically an animation lead.

**Acceptance:** the actual motion reaches required poses/contacts and the director judges the performance in sequence. Technical deformation success alone does not pass expressive acting. Where the rig or generation cannot support the action, return a specific route/action decision before multiplying shots.

### 6. Product/design authority → look/CG/generation (`07/09/20 → 12/13/14/16`)

**Send:** exact geometry/label/identity/text masters with their authority domains, approval status and allowed variation. **Return:** a layer/control plan explaining what must remain exact and where stochastic variation is harmless. A style reference may govern atmosphere, not override packaging truth; a model cannot infer exact dimensions from a visual reference.

**Acceptance:** representative moving views preserve the relevant invariants. Use measured tolerance only when a real requirement and measurement exist. A failed control test is evidence to change route, not permission to relabel the asset approved.

### 7. Camera/look/source interpretation → comp/finish (`11/12/13/14 → 15/19`)

**Send:** actual source elements, known interpretation, relevant camera/space relations, intended look and limitations. **Return:** an integration/grade plan with required holdouts/contact/passes or interpretation corrections. Diagnose the cause: a missing contact shadow, wrong perspective and source-color mismatch require different work. Do not prescribe regeneration for a signal-only color problem.

**Acceptance:** actual temporal playback and adjacent-cut review resolve the located failure under the stated pipeline. A corrected hero still does not establish temporal stability, and a screenshot does not establish original color values. Return unavailable plate/control information as a bounded dependency; do not pretend it was inspected.

### 8. Picture edit ↔ sound/music (`17 ↔ 18`, with `04/05`)

**Send:** actual cut version, available audio/track version, intended cue/reveal/counterpoint and known stem limits. **Return:** a located event/timing comparison and an actual alternative only when made. Sound may carry an unseen relation; a visual pickup may be unnecessary. Conversely a new picture cut may invalidate a sonic reveal or source structure.

**Acceptance:** listen/view the actual revised interval and whole-sequence context. Keep purposeful silence, voiceover and repetition. Do not claim to have heard unavailable channels or treat a paper edit as a tested mix. Rights changes route to20 and only affected use is blocked.

### 9. Exact copy + version framing → graphics/edit (`16/20/21 ↔ 10/17`)

**Send:** approved exact copy/marks, actual language/version requirements and current official/customer specification when needed. **Return:** controlled graphics, meaningful layout/timing changes and a version classification: `MASTER`, `DERIVED_VERSION`, `RECOMPOSED_VERSION`, `NEW_PRODUCTION_UNIT`.

**Acceptance:** inspect exact wording/marks and actual timed contextual readability in every requested affected version. Do not invent universal safe areas or reading times. A dimensionally correct crop can fail the scene; a simple export is not a new concept. Accessibility/localization requirements must be explicit, and subtitles alone do not certify accessibility.

### 10. Approved cut → conform/master → recipient (`17/19 → 21`, custody22)

**Send:** the actual approved edit/reference, source IDs, requested export/project deliverables and recipient workflow. **Return:** corresponding masters and per-file discrepancy/QC record. Distinguish a viewable export, a correct conform, a delivered download and a recoverable editable project.

**Acceptance:** perform relevant frame/order/crop/text/sync/decode checks on actual media. Test relink/restore/transfer if requested; record real results and real recipient acknowledgement only when they exist. A link, export success or CI pass is not recipient acceptance. If the timeline changes, recheck affected conforms/versions while preserving unrelated validated work.

### 11. Claim/use/permission → dependent execution (`20 → affected functions`)

**Send:** exact assertion/asset/use, known evidence and limits, decision owner and relevant version. **Return:** verified wording/permission or an approved replacement route through the actual authorized person. A missing uploaded licence is an open evidence boundary, while an explicit exclusion is a known constraint.

**Acceptance:** actual owner/qualified review resolves the required use; AI advice does not grant rights or certify legal compliance. Do not click declarations, disclose private references, transfer files or submit anything without appropriate user authorization. Noncommercial work is not automatically exempt from rights concerns. Keep independent creative work moving where safe and authorized.

### 12. Findings → production scope → studio decision (`affected functions → 22`, consuming01/20/21)

**Send:** supported findings, preserved strengths, critical dependencies, useful DIY/existing-team routes and countable work units. **Return:** required-now work, conditional extension after a test, and optional improvements. State assumptions and identify actual unknown counts, rates, times, capability and capacity rather than inventing them.

**Acceptance:** a real human can assess exactly what is proposed, why, what inputs unlock it and how to accept it. Studio agreement/estimate/booking exists only after actual human confirmation. Objekts digital-production opportunities follow evidence; physical filming, research, casting, legal clearance, specialist safety and music licensing are not presumed included services. Do not manufacture an obstacle to force a lead or present a preview as a sent handoff.

## Scope example — conditional, not a client result

**Illustrative fictional condition:** a supplied moving product turn visibly changes the approved label in two identified shots; the remaining shots are already usable. An exact label master is not in the submitted set.

The audit can identify the visible inconsistency now. Exact repair depends on obtaining or confirming a legitimate authoritative master; it must not declare that no master exists. A useful scope is: verify the approved master and source interpretation; build/reuse one controlled product layer; test the critical turn/contact in one representative moving interval; after that test, integrate into the two affected shots and inspect them at the actual cut. If the source does not permit replacement, compare a different usable cut or a new controlled shot. Count asset preparation once and shot-specific integration separately.

Required functions are a decision owner and the relevant digital asset/comp skill; these may be one qualified person. A studio may be useful for controlled asset construction and integration if those capabilities/capacity are confirmed. A DIY route may suffice if the creator has the source and competence. No price, promised result, licence approval, render, client acceptance or studio booking is implied by this example.

## Change propagation without administrative theater

When an approved choice changes, preserve the old version and mark directly affected checks `NEEDS_REVALIDATION`. Follow actual consumers, not every possible downstream arrow mechanically. For example: a change of underlying track version may affect source interpretation, edit timing, performance accents and rights without changing an approved product mesh. A label spelling correction may affect graphics/comp/versions without reopening the whole concept. Record returned artifacts and new evidence before closing the affected checks.

Present the user with the requested scale of professional judgment: verdict, strongest supported problems and strengths, concrete interventions, work scope and necessary decision. Keep the register internal unless it helps a decision. Neither “one issue per turn” nor “show three departments” should limit a requested deep audit.
